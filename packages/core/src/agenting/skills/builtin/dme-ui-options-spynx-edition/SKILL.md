# DME UI Options | Spynx Edition — Visual Direction Laboratory vNext

Use this when **structure is sufficiently settled but visual direction is genuinely open**.

When available, load:
- `../../shared/CORE_CONTRACT.md`;
- `../../shared/DESIGN_LANGUAGE_ATLAS.md`.

The purpose is to compare **design theses**, not themes or color swaps.

---

## 1. Entry gate

Use when:
- user asks for visual directions/options;
- product direction is materially ambiguous;
- several plausible visual grammars would change brand/product character;
- a redesign needs deliberate aesthetic exploration before implementation.

Do not manufacture options when:
- repository already has coherent intentional product language;
- user supplied an approved direction/reference;
- uncertainty is information architecture → `dme-wireframe-spynx-edition`;
- the change is a local style repair.

Adaptive behavior:
- if evidence strongly implies one direction, establish it and continue;
- invoke options only when choice can change a material product decision.

---

## 2. Freeze the common truth

All options must solve the same product problem.

Hold constant:
- user/job;
- information architecture;
- content;
- required states;
- primary action;
- product behavior;
- target viewports;
- accessibility obligations;
- critical invariants.

If an option changes task structure, the comparison is dishonest.

---

## 3. Derive the design vector

Identify only dimensions with real freedom:

- restrained ↔ expressive;
- editorial ↔ application-like;
- dense ↔ spacious;
- technical ↔ human;
- serious ↔ playful;
- geometric ↔ organic;
- flat ↔ atmospheric;
- monochromatic ↔ chromatic;
- conventional ↔ experimental;
- quiet ↔ kinetic.

Do not vary every dimension independently.

A direction is a coherent relationship, not coordinates sampled at random.

---

## 4. Select language families contextually

Use product pressure and the Design Language Atlas.

For each candidate language ask:
- Does it fit task frequency?
- Does it support required density?
- Does it match trust/consequence level?
- Does it fit existing brand/product signals?
- Can accessibility survive without exceptions everywhere?
- Can the runtime afford its material/motion cost?
- Does it create identity without fighting product conventions?

A dominant language may have one supporting material/language.

Do not create aesthetic soup.

---

## 5. Generate 2–4 real theses

Each option must differ in **visual logic**, not decoration count.

A thesis should coordinate:
- composition;
- typography;
- density;
- color strategy;
- shape/radius;
- borders/depth/material;
- imagery;
- icon treatment;
- motion character;
- interaction feel.

Different fonts on identical layout are usually one option.

Different accent colors on identical grammar are one option.

---

## 6. Option contract

Give each direction:

- stable ID (`V1`, `V2`, ...);
- memorable mechanism-based name;
- one-sentence thesis;
- audience/product fit;
- dominant design language;
- supporting language/material if any;
- Design DNA;
- product signal amplified;
- signature move;
- counter-default refused;
- typography strategy;
- color/chroma behavior;
- density/spacing behavior;
- geometry/elevation behavior;
- imagery/icon strategy;
- motion character;
- accessibility/performance risk;
- what would make the direction fail.

Avoid names like “Premium”, “Modern”, “Clean”.

Prefer mechanism names such as:
- Signal-First Ledger;
- Quiet Technical Editorial;
- Measured Industrial;
- Warm Operational;
- Spatial Media Control.

Names are handles, not rationale.

---

## 7. Distinctness test

Two options are genuinely distinct only if a reviewer could identify which thesis produced them after:

- removing logo;
- neutralizing accent color;
- inserting the same content;
- viewing in grayscale.

If not, increase divergence in composition/type/density/material logic.

Do not increase random decoration.

---

## 8. Defensible-first exploration

When generating several directions:
- first option should usually be the strongest conservative/defensible fit;
- later options may widen expression or challenge defaults;
- every wider option must remain product-credible.

Do not create a deliberately bad option to make the preferred one win.

---

## 9. Reference translation

If references exist, extract:
- grid;
- composition;
- type relationships;
- density;
- material;
- color behavior;
- shape;
- imagery;
- interaction/motion clues;
- responsive transformation.

Translate those into rules.

Do not say “similar vibe” without implementable consequences.

Do not clone brand, copy, proprietary data, or accidental defects.

---

## 10. Signature move discipline

Each option may have one strong signature move.

It must improve:
- hierarchy;
- comprehension;
- product identity;
- interaction;
- spatial continuity;
- meaningful completion.

Examples:
- type relationship;
- unusual navigation rhythm;
- data composition;
- disciplined accent behavior;
- spatial interruption;
- product-specific framing/divider system.

Do not let every section compete to be memorable.

---

## 11. Genericity firewall

Reject/repair directions that rely on defaults without product reason:

- rounded cards everywhere;
- card-in-card nesting;
- purple/blue gradient identity;
- huge centered hero text;
- universal pills;
- glass on every surface;
- bento fragmentation with no information reason;
- repeated feature triads;
- arbitrary glow;
- decorative blobs;
- tiny uppercase labels everywhere;
- generic “premium dark” cyberpunk;
- component-library defaults visible as the brand.

Ask for every suspicious choice:
`what does this buy for this product?`

If the answer is only “looks modern,” remove it.

---

## 12. Comparable rendering

When render/browser capability exists, compare options under the same evidence conditions:

- same viewport(s);
- same copy/data;
- same product state;
- same imagery availability;
- same functional controls.

Do not let one option win because it got richer content.

At minimum inspect:
- representative desktop/wide;
- one narrow/stress width if responsive composition matters.

For high-stakes direction selection, include a key interaction or state.

---

## 13. Perceptual tests

For each serious option:

### Squint
Does macro hierarchy remain obvious?

### Grayscale
Does type/luminance/spacing still create hierarchy?

### Silhouette
Does composition feel intentional without text/color?

### Density
Are surfaces doing real grouping work, or could several containers disappear?

### Logo-off
Would this still feel product-specific?

### Decoration budget
Is there one dominant effect/signature or several competing ones?

---

## 14. Risk analysis

For each direction identify:
- readability risk;
- contrast/transparency risk;
- density mismatch;
- motion/vestibular risk;
- responsive fragility;
- asset dependence;
- font payload/licensing;
- filter/3D/WebGL cost;
- implementation complexity;
- design-system divergence;
- maintenance risk.

Do not hide engineering cost behind aesthetic enthusiasm.

---

## 15. Selection logic

A direction wins because it best balances:

1. product fit;
2. user comprehension;
3. interaction fit;
4. accessibility;
5. existing product/brand coherence;
6. responsive viability;
7. performance;
8. identity/distinctiveness;
9. implementation cost.

If one risk is disqualifying, aggregate scoring does not save the option.

When evidence is strong, recommend a winner and explain the dominant trade-off.

Do not end with “it depends” unless the missing preference genuinely changes the product.

---

## 16. Refinement after selection

Once selected:
- freeze the dominant language;
- retain the signature move;
- retain the counter-default;
- refine tokens/type/material/spacing coherently;
- do not hybridize rejected options casually.

If the user asks:
“V2 but less glass and denser”
modify those dimensions while preserving V2’s identity.

Do not silently create V4.

---

Produce or internally preserve:

```text

```

Implementation and design-system work inherit this contract.

---


## 18. Verification

Before freezing a direction, verify that the winning thesis survives the representative content, viewport, state, and perceptual tests actually relevant to the product.

Do not call a direction validated if it was never rendered when rendering capability existed.

State any visual, accessibility, or performance assumptions that remain unverified.

## 19. Exit gate

Finish when:
- common product truth stayed fixed;
- options were only generated when choice mattered;
- directions are genuinely distinct;
- each has coherent Design DNA;
- generic defaults were challenged;
- relevant options were rendered when possible;
- risks are visible;
- one direction is selected/recommended;
- handoff contract is stable.

The purpose is not to maximize the number of concepts.

It is to remove visual ambiguity before code hardens it.

---

## Standalone core capsule

If shared references are unavailable: preserve product structure and behavior; generate options only when choice is material; derive direction from user/job/density/trust/performance; keep one dominant language; challenge generic patterns; compare with same content/state; state risks; converge on one Design DNA and do not reopen it without new evidence.
