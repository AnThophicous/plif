# DME UI Options | Spynx Edition — Visual Direction Laboratory

Use this only when visual direction is genuinely unresolved.

The purpose is to compare **design theses**, not themes.

Do not manufacture options when:

- the repository already has a deliberate product language;
- the user supplied an approved reference;
- a selected direction already exists;
- the real uncertainty is information architecture — use `dme-wireframe-spynx-edition`.

## 1. Freeze the common truth

All options must solve the same product problem.

Hold constant:

- user;
- job;
- information architecture;
- content;
- required states;
- primary action;
- functional behavior;
- target viewports;
- accessibility obligations.

If options change product structure, the comparison is dishonest.

## 2. Build a design vector

Before generating directions, identify the dimensions with meaningful freedom:

- restrained ↔ expressive;
- editorial ↔ application-like;
- dense ↔ spacious;
- technical ↔ human;
- serious ↔ playful;
- geometric ↔ organic;
- flat ↔ atmospheric;
- monochromatic ↔ chromatic;
- conventional ↔ experimental;
- static ↔ kinetic.

Do not vary every dimension independently. A direction should be coherent.

## 3. Generate 3-5 theses

Each option must contain a strong internal relationship between:

- composition;
- typography;
- density;
- color strategy;
- shape language;
- surface/depth;
- image treatment;
- icon treatment;
- motion character.

Color swaps of one layout are one option.

Different fonts on identical composition are usually one option.

Every option should have a reason to exist.

## 4. Option contract

Give every direction:

- stable id;
- memorable name;
- one-sentence thesis;
- intended audience/fit;
- product signal it amplifies;
- signature move;
- counter-default it refuses;
- typography role;
- color behavior;
- density behavior;
- surface/shape language;
- motion character;
- accessibility/performance risk;
- what would make the direction fail.

Avoid empty names such as "Modern", "Premium", or "Clean."

Name the mechanism:

- "Editorial Control Room";
- "Measured Industrial";
- "Warm Technical Ledger";
- "Signal-First Minimal";
- "Kinetic Catalog".

Names are handles, not substitutes for explanation.

## 5. Distinctness test

Two concepts are different only if a user could identify which thesis produced them with:

- logo removed;
- accent color neutralized;
- same content inserted.

If not, increase structural visual divergence.

The options should differ in visual logic, not decoration count.

## 6. Start from defensible, then widen

Option ordering should usually move from:

1. repository-native / restrained;
2. stronger interpretation of product character;
3. distinctive but highly shippable;
4. more experimental if justified;
5. edge direction only when useful for comparison.

Do not make later options intentionally bad to make the first one win.

Every presented option must be credible enough to ship if selected.

## 7. Signature move discipline

Each direction gets one dominant memorable move.

Examples:

- asymmetric editorial index;
- edge-anchored command rail;
- high-contrast data typography;
- controlled single-accent navigation state;
- full-bleed media rhythm;
- layered document surfaces;
- responsive type-led composition.

The move must improve identity plus at least one of:

- hierarchy;
- scanability;
- comprehension;
- navigation;
- continuity.

If it only makes the screenshot dramatic, it is decoration.

## 8. Anti-generic test

Reject a direction when:

- it relies on cards for every group;
- it has no identity after logo removal;
- it looks like untouched component-library defaults;
- its personality is mostly gradient/glow;
- it repeats standard landing-page rhythms;
- all hierarchy comes from font size;
- it uses motion as visual noise;
- its "premium" quality comes only from excess whitespace;
- it invents fake data/proof to make the composition work.

Do not fix genericity by adding more effects.

Change the design thesis.

## 9. Comparable rendering

When producing actual visual options:

- use the same content;
- use the same target viewport;
- show comparable completeness;
- include the same major states where relevant;
- preserve accessibility obligations;
- avoid making one option more polished than the others.

If browser or rendering capability exists, inspect the actual options rather than comparing code.

## 10. Risk analysis

For each option, identify real trade-offs.

Examples:

- expressive display face may increase font cost or reduce dense-data usability;
- split composition may become awkward at intermediate widths;
- strong animation concept may conflict with reduced-motion and low-power devices;
- very dense visual language may require stronger onboarding for novice users;
- unusual navigation may carry discoverability cost.

Do not reject all risk. Distinctive design often has cost.

Choose risks the product can afford.

## 11. Selection

Recommend based on:

`product fit × differentiation × usability × accessibility × performance × implementation coherence`

Do not reduce selection to personal taste.

If user/project evidence chooses a direction, stop generating alternatives.

Record:

- selected id;
- thesis;
- signature move;
- counter-default;
- core coherence laws;
- known risk to watch during implementation.

Pass that contract to `dme-front-end-spynx-edition` and `dme-visual-verification-spynx-edition`.

## 12. Refinement

When the user says "more like B, but calmer":

- preserve B's identity;
- identify which dimension should move;
- change that dimension intentionally;
- keep stable ids or derive a clear child id.

Do not accidentally mutate the entire concept.

## 13. Exit gate

This phase is complete when one direction is selected strongly enough that implementation no longer has to invent:

- visual voice;
- signature move;
- density stance;
- type behavior;
- color behavior;
- shape/depth language;
- motion character.

The goal is commitment, not option proliferation.
