# PLIF 0.4.0 Runtime, Persistence, Safety and Distribution Design

Date: 2026-08-29
Status: Proposed for implementation review
Release: 0.4.0

## Summary

PLIF 0.4.0 is a reliability release across five connected surfaces: package
distribution, complete conversation history, isolated subagent sessions,
project-scoped memory and environment credentials, and a safer terminal
composer. The product remains a terminal-first coding agent. The parent agent
and every subagent are independent conversation lanes with explicit ownership;
the parent receives results from a child without importing the child's private
transcript.

The CLI remains TypeScript running on Node.js `>=20.11`. The updater is a
separate pure-Rust executable bundled in the NPM package for Windows and Linux.
SQLite is used for both history and memory, but in separate databases. NPM is
the only update source.

## Product goals

- Keep every user and agent action recoverable after rendering, interruption,
  restart, compaction, or a provider failure.
- Make a subagent behave like an independent main agent that serves a parent
  agent without merging their conversations.
- Give a child a stable, bounded fork of the parent's useful context on its
  first request and support later turns on the same child.
- Make global memory and active-project memory useful without allowing memory
  or environment values to cross project boundaries.
- Keep secrets out of model-visible context by default and make accidental
  secret submission difficult to do silently.
- Handle interactive terminal programs through a persistent terminal session,
  not a one-shot stdin buffer.
- Add local writing assistance without sending drafts to a remote spelling or
  completion service.
- Make installation and updates predictable on Windows and Linux, including
  x64 and ARM64.

## Non-goals

- Git is not an update or changelog source.
- C# and a DLL are not part of the updater.
- Subagents do not write, edit, delete, or merge persistent memories.
- Parent and child events are not copied into one another's visible transcript.
- Portuguese is not the default interface language; user-facing PLIF text is
  English by default.
- Cloud-backed spellchecking or a mandatory local language model is not part
  of the base 0.4.0 composer.
- macOS updater artifacts are outside the 0.4.0 target matrix.

## Architecture alternatives

### Option A: Extend the current JSONL and Node-only runtime

This would make the smallest local diff, but it keeps the failure modes that
are being corrected: projections can diverge from the canonical transcript,
concurrent writes remain difficult to reason about, and an updater inside the
running Node process cannot reliably replace its own package. It also does not
provide the requested isolated Rust updater.

This option is rejected.

### Option B: Make the whole runtime native-first

A native Rust runtime, native SQLite binding, native keyring integration, and
Rust updater would provide strong process primitives. It would also turn the
0.4.0 release into a rewrite, add native build and distribution failures to
the NPM install path, and make Node 20.11 plus Windows/Linux ARM64 support
harder to keep reproducible.

This option is rejected for this release.

### Option C: Keep the CLI in TypeScript and isolate the native boundaries

The recommended architecture keeps the existing CLI and harness, adds a
SQLite repository boundary, uses a portable SQLite implementation without a
mandatory native addon, delegates OS credential storage to platform adapters,
and packages a standalone Rust updater. The CLI remains easy to install from
NPM while the updater remains replaceable and isolated from the process it
updates.

This option is selected. Exact package/library choices belong in the
implementation plan, but they must preserve Node 20.11, Windows/Linux x64 and
ARM64, and the no-native-addon baseline for the normal CLI install.

## Ownership and identity

Every conversation lane has:

- a stable full UUID used for fork metadata and durable relationships;
- a short compatibility identifier where existing session UX expects one;
- an owning workspace key;
- a provider/model route snapshot;
- a lifecycle state;
- a parent session UUID and parent checkpoint sequence when it is a fork.

The parent-child link is metadata, not shared transcript state. The child is
identified in its own first visible context with:

```text
Forked from ID-<parent-full-uuid>
```

The full UUID is never reconstructed from a display label. Existing short
session IDs remain resolvable during migration.

## SQLite history

The canonical conversation database is:

```text
~/.plif/history.db
```

It is separate from `memory.db`. The database contains at least:

- `sessions`: UUID, compatibility ID, workspace key, title, parent UUID,
  fork checkpoint, provider/model route, timestamps, and lifecycle state;
- `events`: session UUID, monotonic sequence, event UUID, turn UUID, type,
  timestamp, and versioned JSON payload;
- `checkpoints`: session sequence boundaries and the context snapshot used to
  create a fork or rebuild a model request;
- `queued_inputs`: target session, input UUID, text/attachments, enqueue time,
  delivery sequence, and delivery status.

Every event is addressed by its owning session UUID. The UI must never build a
child transcript by filtering parent rows or build a parent transcript by
flattening child rows. A child history view queries the child's own session
rows and may show the parent UUID as provenance only.

### Write and replay rules

- User messages, assistant messages, reasoning summaries, tool starts, tool
  completions, command input, terminal output, approvals, questions, errors,
  cancellations, interruptions, compaction boundaries, queued inputs, and
  final answers are durable events.
- A single append queue serializes writes inside a process. SQLite transactions
  and a short cross-process lock protect read-modify-write operations.
- WAL mode, foreign keys, a busy timeout, and atomic migration steps are
  enabled by the repository adapter.
- The UI consumes the same canonical append stream used by replay. A live row
  is not treated as the source of truth merely because it rendered first.
- Compaction writes a checkpoint and a model-facing summary. It never deletes
  raw events.
- History is retained indefinitely by default. Explicit cleanup is a separate
  user action and must state exactly which session data it removes.

The existing JSONL sessions are imported once on first access. Import preserves
event order and legacy identifiers, records an import marker, and leaves the
source files untouched until the migration succeeds. A failed migration can
be retried without silently dropping the original data.

The normal transcript shortcut continues to open the complete history for the
currently focused lane. When a subagent is focused from the work dock, the
transcript view switches to that child and shows its own full event stream;
the parent view remains unchanged.

## Subagent fork and continuation

### First request

When the parent calls `subagent`, PLIF performs these steps:

1. Flush the parent event queue and create an immutable checkpoint at the
   latest complete model-facing boundary.
2. Create a child session with a new full UUID and a separate event stream.
3. Store the parent session UUID, checkpoint sequence, workspace key, model
   route, and title in the child manifest/session row.
4. Copy the useful parent model context through the checkpoint: user requests,
   assistant answers, relevant tool calls/results, approvals, failures, and
   active task state.
5. Bound or compact the copy when it is too large. The compact form preserves
   the current objective, completed actions, assumptions, identifiers,
   unresolved blockers, and next action rather than taking an arbitrary tail.
6. Build the child system prompt from the child route and child tools. The
   parent's system prompt is not copied as a second competing system prompt.
7. Add the `Forked from ID-<parent-full-uuid>` marker, the forked context, and
   the delegated task to the child's first request.

The copied context is a snapshot. Later parent events do not appear in the
child automatically, and child events do not appear in the parent
automatically.

### Child isolation

The child owns its own:

- provider request sequence and turn IDs;
- SQLite history rows;
- event bus and live terminal sessions;
- queued inputs and tool results;
- model/provider metadata;
- final answer and lifecycle state.

The parent receives a start event, bounded progress, completion status, final
answer, child ID, and a history reference. It does not receive the child's
individual messages or tool rows in its own transcript. The work dock may show
a compact live status, but the dedicated child history is the authoritative
place to inspect all child actions.

### Follow-up turns

`send_message` continues a persisted child instead of creating a replacement.
It is serialized per child: one child model turn may run at a time. A parent
input received while a child is inside a tool call is appended to that child's
queue and does not interrupt the in-flight tool call. At the next model
boundary, the child request is built in this order:

1. the assistant tool call(s);
2. their tool result(s);
3. queued parent inputs in enqueue order;
4. the next provider request.

Each queued input remains a durable user event. Multiple inputs are not
silently merged or routed to another child. If a child has finished, the next
`send_message` resumes it from its stored conversation and runs the same
boundary logic.

The parent may cancel a child explicitly. Cancellation is recorded in the
child history and does not delete the child or its previous turns.

## Interactive terminals

The current buffered `stdin` option remains useful for simple commands but is
not an interactive terminal. 0.4.0 adds a persistent terminal session owned by
one conversation lane. The conceptual operations are:

- start a terminal and receive a terminal ID;
- write input to that terminal;
- read output or wait for the next output/exit event;
- resize the terminal;
- send a supported signal or interrupt;
- close the terminal and persist its final state.

The Linux implementation uses a PTY. The Windows implementation uses ConPTY.
Both implementations expose the same core lifecycle and enforce the owning
session and container boundary. A terminal ID from the parent cannot be used
by a child, and a child terminal cannot appear in the parent's terminal rows.

Starting a terminal passes through the existing PLIF execution policy. Input
to an already approved terminal is delivered to that process, while dangerous
new process creation still requires the normal policy decision. Terminal
output is streamed to the owning lane, persisted as bounded chunks, and
redacted for known `/env` values before it reaches UI, logs, or model context.

If PLIF exits while a terminal is alive, the process is terminated and the
terminal is recorded as interrupted. Reattachment is not promised in 0.4.0;
the history retains the last output and the reason it could not continue.

## Memory database

The memory database is separate from conversation history:

```text
~/.plif/memory.db
```

It contains a global scope and workspace scopes. A workspace scope is keyed by
the canonical active project path, including platform-specific normalization.
The main agent loads global memory plus the active workspace memory. A session
in another folder does not query the previous workspace scope.

The memory repository stores versioned records with a scope, canonical
workspace key when applicable, content, kind, tags, timestamps, confirmation
state, contradiction state, and active/deleted state. It uses the same
transaction and migration discipline as history but never shares its database
file with history.

The public agent surface is one lightweight tool:

```text
remember(content, scope?)
```

The agent decides intentionally what is worth retaining. It does not cause
the whole conversation to be captured automatically. `workspace` is the safe
default; `global` is an explicit choice for information that should apply to
all sessions. Retrieval combines global and active-workspace records using the
existing relevance/confirmation ranking.

At a fork, the child receives a read-only snapshot of the applicable global
and workspace memory. The child may use those facts while working, but it has
no memory-write tool and all write attempts are denied at the core boundary.
Memory changes made later by the parent are not injected into an already
running child.

Existing JSON memory records are imported into the appropriate SQLite scope
without deleting their source until the import is verified. Conflicting
records remain distinguishable during migration instead of being overwritten
silently.

## Project environment and `/env`

Environment values are project-scoped, like workspace memory. Sessions opened
in the same canonical project may use that project's environment. A session in
another project cannot load those values. The active project key is part of
the storage binding and is never inferred from a display name.

At PLIF bootstrap, the project environment is loaded into the controlled
runtime environment. Main-agent commands, child-agent commands, providers,
and persistent terminal sessions inherit the project environment as needed.
The values are never inserted into model messages, system prompts, status
screens, history events, audit output, or ordinary logs. `/env` exposes names
and status, not values.

Changes made through `/env` update the store and the runtime environment for
subsequent processes. A process that is already running keeps the environment
with which it was created.

### Storage backends

- Windows uses Windows Credential Manager by default.
- Linux uses Secret Service by default.
- If the native backend is unavailable, PLIF uses an encrypted local fallback
  and shows a reduced-protection warning. It never writes plaintext secrets.
- The fallback uses one user-provided passphrase for the local vault. The
  passphrase is requested when the vault must be unlocked, is never persisted,
  and is held only in memory. Project records remain separated inside the
  vault.

The backend boundary returns values only to the controlled execution layer.
Tool output and terminal output pass through secret redaction before reaching
the transcript or model. The harness forbids deliberate commands that print
or enumerate secret values. Credentials pasted into chat are never treated as
approved `/env` values.

Subagents inherit the project's controlled environment so they can perform
legitimate serious tasks, but their model context still cannot see the values.
Automated use of passwords or private credentials for `sudo` and other
privileged authentication remains disallowed; the user must complete that
interactive authorization themselves.

## Secret detection and harness policy

The composer scans draft text locally before provider submission. A token-like
value beginning with `sk_` is the first high-confidence detector, with room for
additional API-key, bearer-token, private-key, password, and database-secret
patterns. Detection never calls a provider or sends the draft over the
network.

The first warning is English and explains that the secret may be saved in chat
history and sent to the model provider. It directs the user to `/env`.

If the user presses Enter while the warning is active, a final confirmation
appears with these actions:

- `Cancel and Edit`;
- `Save Redacted Prompt and Cancel`;
- `Send Anyway`.

The redacted action removes the detected secret, stores the safe draft for the
composer's up-arrow history, and may copy only that redacted draft to the
clipboard. The original secret never enters that clipboard path.

`Send Anyway` is an explicit override. PLIF sends and persists the original
prompt using normal behavior after that confirmation and does not keep
interrupting the user. The harness still refuses to use, repeat, transform,
or forward a secret that originated in chat. It clearly tells the user that
the secret may have reached the provider's servers and must be revoked or
rotated immediately.

The core harness instruction is equivalent to:

```text
Treat credentials pasted into chat as compromised. Never use, repeat,
transform, or forward them, including API keys, database credentials, bearer
tokens, private keys, passwords, or privileged credentials. Use only approved
values made available through /env, and keep their values out of model
context, prompts, transcripts, logs, previews, and tool output. If a user
explicitly sends a credential anyway, do not use it; explain that it may have
reached the provider and instruct the user to revoke or rotate it.
```

## Model identity

The runtime prompt context carries the selected provider ID, exact model ID,
display name when available, endpoint route, and capability metadata. The
harness instructs the agent that PLIF is the host/orchestrator, not the model.

When asked what model is running, the agent answers with the actual provider
and model route. If the runtime does not expose a field, it says that the
metadata is unavailable instead of inventing a model. The same metadata is
available to status and history surfaces without exposing credentials.

## Installer and updater

### Installation

The primary path remains:

```text
npm install -g @plif/cli@latest
```

PowerShell on Windows and Bash on Linux are supported secondary installers.
They perform the same Node preflight, use NPM for package installation, show
English setup text, and ask whether automatic update notifications should be
enabled. The default is enabled, and the choice is stored per user.

### Updater artifacts

The updater is a standalone Rust executable bundled inside the published CLI
package under platform/architecture-specific assets. The 0.4.0 matrix is:

- Windows x64;
- Windows ARM64;
- Linux x64;
- Linux ARM64.

The Linux updater is built as a portable self-contained executable where the
target permits, and neither platform requires a C# DLL. The updater is not
linked into the main Node process and is launched as a separate process only
after the user approves an update.

### NPM-only update flow

1. At startup and every six hours, PLIF checks the NPM registry for the latest
   published `@plif/cli` version. The check is non-blocking.
2. Offline or failed registry checks produce no user prompt and retry at the
   next interval.
3. When a newer version exists, PLIF obtains the exact NPM package metadata and
   tarball for that version. Git and GitHub are not consulted.
4. PLIF reads the target package's `CHANGELOG.md` section before installation
   and displays it in English.
5. The user chooses `Update now`, `Later`, or `Don't ask again`. The latter is
   stored for that target version only, so future releases can notify again.
6. For `Update now`, PLIF records the decision, finishes the active turn safely,
   starts the bundled Rust updater, and exits cleanly.
7. The updater verifies package identity/version/integrity, runs the NPM global
   install for the exact target version, verifies the resulting CLI, and
   relaunches the same PLIF entry point when possible. Failure leaves the
   existing installation in place and reports a recoverable diagnostic.

The updater never updates from a Git checkout and never treats a missing or
unversioned changelog as acceptable. Release validation requires the root
`CHANGELOG.md` to contain the target version and requires the published CLI
tarball to contain that document and the correct updater asset.

## Composer assistance

The `/settings` surface exposes local autocomplete and language. The predictor
uses a compact local dictionary plus weighted bi-gram and tri-gram transitions
from recent prompt history and project vocabulary. Draft text is never sent to
a remote completion or correction service.

Suggestions appear as a single ghost suffix inside the prompt. `Tab` accepts
the best contextual prediction; `Enter` always submits the draft, and no keypress
silently rewrites it. Commands, paths, URLs, code, identifiers, environment
names, tokens, and secrets stay outside the predictor.

Emoji completion remains text-native. The catalogue and aliases expand, and a
selection such as `:rocket:` becomes `🚀` before submission. The model receives
the emoji as ordinary Unicode text; PLIF does not upload an image or create a
file attachment.

## Queue and turn semantics

Each conversation lane has its own input queue. Main-agent inputs stay with the
main lane; parent follow-ups target a specific child ID; terminal input targets
a specific terminal ID. No queue is globally drained into whichever agent
happens to be visible.

When a lane is waiting inside a tool call, queued inputs remain visible as
pending UI state and durable queue events. They are delivered exactly once at
the next safe model boundary, after the relevant tool results and before the
next provider request. This makes the model see the action result and the new
instruction in one coherent turn while preserving the original event order.

## Release and compatibility requirements

The release pipeline must:

- build and test the CLI/core/sandbox packages on Windows and Linux;
- build Rust updater artifacts for Windows/Linux x64/ARM64;
- verify the NPM package includes `CHANGELOG.md` and the matching updater;
- validate the changelog version before publishing;
- exercise history migration from existing JSONL sessions;
- exercise memory migration from existing JSON records;
- test native credential backends and passphrase fallback through injected
  test adapters;
- test secret detection, redacted draft recovery, and explicit `Send Anyway`;
- test parent/child event isolation, fork provenance, follow-up queues, and
  read-only child memory;
- test interactive terminal input/output and ownership on both platforms;
- test local contextual prediction, inline ghost rendering, Tab acceptance,
  Enter submission, protected spans, and Unicode emoji submission.

New production source added for this release follows the project's no-comment
code requirement. Existing comments are not part of the product contract and
do not need a broad cleanup unrelated to these changes.

## Acceptance criteria

The release is ready only when all of the following are demonstrable:

1. A restarted session shows every prior command, tool result, approval,
   failure, user input, and agent response from SQLite history.
2. Compaction reduces model context without removing any raw history row.
3. A child shows its fork marker and copied checkpoint context, while its
   detailed actions remain absent from the parent transcript.
4. A parent can send multiple follow-ups to the same child and observe them
   delivered in order after the child's tool results.
5. A child can read applicable memory and use project environment values, but
   cannot write memory or cross into another project's scopes.
6. A terminal that asks for input can remain alive across tool calls on Windows
   and Linux, and its output is durable in the owning lane.
7. A draft containing `sk_` produces the two-stage English warning; the safe
   action preserves a redacted draft, and `Send Anyway` is the only explicit
   bypass.
8. Asking the agent which model is running returns the configured provider and
   model route, or an honest unavailable-metadata answer.
9. The updater checks only NPM, stays silent offline, shows the target
   changelog, and updates only after confirmation.
10. A fresh install works through NPM and the supported PowerShell/Bash paths
    on Windows/Linux x64/ARM64 without requiring C# or a native CLI addon.
